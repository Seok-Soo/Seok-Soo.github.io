01

부하 발생기와 서버의 병목을 분리해 추적

20,000 VU ramp-up · 쿠폰 재고 10,000장

문제
대규모 요청에서 응답 지연이 발생할 때 서버와 부하 발생기 중 어느 구간의 영향인지 구분할 필요가 있었습니다.
원인
성공 수량 행의 X-lock 경합과 부하 발생기의 Docker NAT 구간이 함께 영향을 줄 수 있었습니다.
해결
두 구간을 분리해 추적하고 부하를 두 장비에 분산했습니다. k6는 Windows 네이티브로 실행했습니다.
평가
발급 10,000건, 품절 10,000건, 전송 실패 0건을 기록했습니다. 평균 응답 시간은 336.95ms, p95는 951.19ms였습니다.
고찰
이 수치는 해당 환경의 ramp-up 결과이며, 20,000명이 한순간에 요청하는 burst 결과와는 구분해야 합니다.
02

대량 데이터 검사에 일관된 조회 기준 적용

사용자 약 100만 · 요청 약 350만 · 사용자 쿠폰 약 79만

문제
많은 데이터를 검사하면서 실행이 겹치거나 조회 시점이 달라지면 결과 해석이 어려워집니다.
원인
검사 실행의 중복과 검사 중 데이터 변경은 서로 다른 문제이므로 각각 제어할 필요가 있었습니다.
해결
MySQL named lock과 읽기 전용 스냅샷을 적용했습니다. 검사와 결과 저장 트랜잭션을 분리하고 중단된 실행 이력 복구를 구현했습니다.
평가
검증 데이터셋에서 중복·초과 발급·상태 불일치 등 정합성 위반 0건을 확인했습니다.
고찰
검사 결과는 해당 스냅샷과 검사 항목에 대한 결과입니다. 이후 발생한 변경까지 보장하는 수치는 아닙니다.
03

검증부터 배포까지 변경 이력 연결

GitHub Actions · Self-hosted Runner

문제
변경이 반영될 때 테스트 결과와 배포 이력을 함께 확인할 수 있는 흐름이 필요했습니다.
원인
이슈, 브랜치, PR, 검증, 배포 기록이 분리되면 변경 원인을 역추적하기 어렵습니다.
해결
PR마다 MySQL·Redis·Kafka 기반 테스트를 실행하고 dev 반영 시 Docker Compose로 자동 배포하도록 구성했습니다.
평가
Jira 이슈부터 브랜치, PR, 검증, 배포까지 변경 이력을 연결했습니다.
고찰
자동 배포 성공과 서비스 기능의 정상 동작은 별도 확인 대상입니다. 배포 자동화 자체를 무장애 운영의 근거로 해석하지 않습니다.

사용 기술Java · Spring Boot · MySQL · Redis · Kafka · Docker · GitHub Actions · k6

01

인증을 토큰 발급부터 재발급까지 연결

JWT · Refresh Token Rotation

문제

원인
Access Token 발급만으로는 만료 이후의 인증 유지와 Refresh Token 교체를 처리할 수 없습니다.
해결

평가
토큰 발급과 재발급을 연결하고 Refresh Token 회전 구조를 적용했습니다.
고찰
구현 범위를 정리한 결과이며, 토큰 재사용 공격 탐지나 동시 재발급 테스트 결과는 이 문서에 포함하지 않았습니다.

고찰
권한 설계와 실제 요청 차단 검증은 구분해야 합니다. 여기에는 정량 테스트 결과를 추가하지 않았습니다.
